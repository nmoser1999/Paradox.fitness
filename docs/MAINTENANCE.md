# Maintaining the website

## Regular content edits

Change business information, FAQ answers, pricing, or checkout URLs in `src/data/site.ts`. Most page prose lives in its `.astro` page. Some offers are repeated in page descriptions and service copy, so search the repository for the old value when changing one. Keep checkout terms, FAQ answers, metadata, and the privacy page consistent. The source proposal records historical research and should not be mistaken for live commercial terms.

Replace the photo at `assets/unnamed.jpg` with the final approved image. If dimensions or aspect ratio change substantially, review desktop/mobile crops and update the original design explorer’s intrinsic dimensions as needed. Production images are generated by Astro; never edit files under `dist/` by hand. Add testimonials only with real text and publication permission.

For styling, update shared component rules and Studio cobalt tokens in `src/styles/global.css`, panorama framing in `src/styles/appearance.css`, and dark tokens and the light/dark control in `src/styles/color-mode.css`. The approved fixed Studio/panorama design lives in `src/lib/design.ts`; the main site ignores legacy design preferences and query overrides. Keep color contrast, focus states, reduced-motion behavior, and mobile touch targets. CTA labels and icons belong inside `ButtonLoad.astro`; its reveal styling lives in `src/styles/buttons.css`. Keep shared button padding variables aligned with the visual copy, and preserve a square SVG viewport when changing the plate. `DirectionsLink.astro` shares this button treatment; keep its Maps icon, native destination/new-tab behavior, and button padding variables, and avoid adding `inline-link` styles to its callers. Keep native click activation; the shared buttons have no click-specific animation, impact markup, or feedback script. Do not add embedded social feeds, video backgrounds, web-font downloads, or third-party widgets without measuring their cost.

Homepage and coaching-page card cutouts live in `ServiceCorner.astro`. The coaching pages use `ServicePanel.astro` to reuse the card treatment with page-specific slot content; keep prices and commercial terms in the original pages and shared data. The in-person icon scales `EQUIPMENT_GEOMETRY.dumbbell.path` from `training-equipment.ts` and angles the whole object together at 45 degrees. Keep the field and icon on that shared outline with a plain handle and closed plate/end-cap contours. Preserve the square in-person viewport and the online corner’s 4:3 viewport/CSS width ratio so icon geometry stays intact. Keep the section-matching `--paper` fill, palette tokens, pointer transparency, and decorative accessibility attributes. Retain the 801px desktop breakpoint and width-based label clearance; check both modes and the narrowest desktop width after changing the corner size or artwork. Keep comfortable insets between the online screen, diagonal, and outer corner.

The optional training field is bounded in `src/lib/training-network.ts`, `src/lib/training-interaction.ts`, and `src/lib/training-drag.ts`. Preserve its node/link/pixel limits, passive mouse movement, idle-work cutoff, and listener cleanup. Only prevent the pointer-down default after a valid equipment pickup. Preserve square equipment grab regions and their padding, pointer-capture cancellation, rigid grab offsets, opaque reading surfaces and interactive controls, release-click suppression, and restoration of the original drift. Keep drag positioning in the existing frame loop. Plain text over visible equipment must remain eligible for pickup; do not exclude generic heading or paragraph tags. Restore hover from the actual surface beneath a released pointer. Keep pointer geometry reads out of the animation loop, and update both drawing and attachment transforms together. Equipment details and weight markings belong in `src/lib/training-equipment.ts` so the canvas and fallback SVG stay aligned.

## Change and release routine

1. Create a short-lived branch, make a focused change, and update relevant docs/tests.
2. Run `npm run format`, then `npm run verify` and `npm run format:check`.
3. Review the Netlify deploy preview. Its `/design/` explorer remains available and indexing stays off.
4. Test the actual affected user path, including keyboard/mobile where relevant. For form changes, prove Netlify storage and notification delivery again.
5. Review the diff and merge the approved change. Confirm the resulting production deploy and retain a known-good rollback version.

The GitHub workflow checks both public and review configurations. Netlify’s own build also runs verification. A green code check does not prove DNS, provider configuration, email delivery, or a Lighthouse score.

## Dependencies

Use Node 24 and `npm ci`. Periodically review `npm outdated` and `npm audit`; read framework release notes before major changes. Update dependencies on a branch, commit the lockfile, and run the release checks. Do not use blanket forced audit upgrades that introduce unreviewed breaking changes. Keep GitHub Actions versions current after reviewing the official actions.

## Lead operations

The owner should check the Netlify submissions dashboard and spam classification, monitor the notification inbox, and follow up through the business mailbox. Agree a retention/deletion period appropriate to actual operations and update the privacy page to match. Export records through the provider only when needed and store exports securely. Avoid committing leads, exports, or screenshots with personal information.

If leads stop arriving, check in this order: site availability/usage allowance, form registration, stored submissions, spam classification, notification recipient/team status, mailbox spam rules, then reply-to behavior. If records are stored but emails are missing, treat that as notification delivery failure rather than asking prospects to resend blindly.

## Hosting and domain upkeep

Review Netlify usage and build notifications, monitor domain/mailbox renewals, and keep billing/account recovery ownership current. Keep DNS records documented before changing providers. A free-plan pause can stop forms as well as page traffic. For code failures, roll back a known-good Netlify deploy and fix/revert the source branch. For DNS problems, restore only the recorded website records; preserve mail records.
